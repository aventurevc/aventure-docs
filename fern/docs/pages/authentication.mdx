This page is for anyone deciding whether a call needs a credential or a plan.
The public API has two access modes:

- An operation with no `security` declaration in the [API reference](/api-reference)
  is anonymous. `GET /v1/entities/summary` and `GET /v1/entities/lookup` are
  examples.
- An operation that declares bearer authentication accepts a personal API key or
  an OAuth access token in the `Authorization` header.

The HTTP method does not decide access, because a `POST` can be a read that
carries a JSON query. Check each operation's security and response declarations.

## Get a personal API key

Any aVenture account can create personal API keys:

1. Sign in to aVenture.
2. Open [your API key settings](https://aventure.vc/settings/api-keys).
3. Choose **Add new key**.

Store the key in your secret manager and load it into the `AUTH_TOKEN`
environment variable at runtime. The same page lists and revokes your keys.

## Sign in from the CLI

`aventure auth login` uses the OAuth device authorization grant. It prints a
one-time code and a sign-in URL, and it works on a laptop, over SSH, and inside
a container. You approve the request at
[your developer access settings](https://aventure.vc/settings/developer), which
also lists past CLI sign-ins and revokes them. `aventure auth login --key`
creates and stores a personal API key through the same approval instead. In a
non-interactive environment, supply an existing key through `AUTH_TOKEN`. The
[CLI quickstart](/cli) walks through each path.

## Connect an MCP client

The [MCP quickstart](/mcp#connect-to-the-hosted-server) lists the hosted URL,
public client ID, and callback settings. MCP requires sign-in even for tools
that call anonymous API operations.

## Verify a credential

Send your personal API key or OAuth access token as a bearer token:

```bash
curl -H "Authorization: Bearer $AUTH_TOKEN" \
  "https://api.aventure.vc/v1/auth/me/permissions"
```

A `200` confirms that the API recognized the token, and the body lists the
permissions it carries.

## Plans and usage

Your aVenture plan decides two things: which features your account can use, and
how much monthly usage it includes. API, CLI, and MCP calls made with your
credential draw on the same account, because the CLI and the MCP server call the
API as you.

- **Anonymous calls** are not charged to any account. Request-rate limits still
  apply.
- **Signed-in reads of one full record** count one profile view against the
  matching company or person allowance. A repeat read of the same record in the
  same calendar month (UTC) is free.
- **Research and enrichment requests** count against the allowance for adding or
  updating a company or person.
- **Features outside your plan**, such as plain-English search on a plan that
  does not include it, answer `402` with `code` `subscription_required`.

Allowances reset at the start of each calendar month (UTC). When an allowance
runs out, the API answers `429` with `limitType` `BILLING_ALLOWANCE` until the
reset. On plans that offer additional usage, you can turn it on so requests
continue past the allowance up to a spending cap you set.
[Allowance limits](/errors#allowance-limits) describes the response fields.

[Your subscription settings](https://aventure.vc/settings/subscription) show
your plan, renewal date, and how much of each monthly allowance you have used.
`GET /v1/billing/subscription` returns the same usage to a signed-in caller, and
`aventure billing subscription get` prints it in the CLI. The
[pricing page](https://aventure.vc/pricing) lists current plans, what each
includes, and its allowances.

## Keep credentials safe

A credential is a bearer secret: anyone holding the string has the access it
grants, and their calls use your allowances. Keep credentials server-side, load
them from a secret manager at runtime, and never ship one in browser code or
commit one to a repository.

## When authentication fails

A missing, malformed, or unrecognized bearer token returns `401`. A recognized
token that lacks permission for an operation returns `403`. Both arrive in the
standard [problem detail](/errors) body, whose `detail` field names the reason.
