Protected aVenture API operations accept the credentials listed in their
`security` declarations. Some operations allow anonymous access. Read each
operation in the [API reference](/api-reference) for its accepted schemes.

## Get a personal credential

Public users can create their own personal API key. Sign in at
[aventure.vc](https://aventure.vc), choose your account menu → **Manage account**,
open **API keys**, and choose
**Add new key**. Store the key in your secret manager and inject it as
`AUTH_TOKEN` at runtime. Never commit or print the key itself. Public users do
not need a client secret or admin API key.

The CLI signs you in for you. `aventure auth login` runs the OAuth device
authorization grant — it prints a one-time code and a URL, and works over SSH
and in containers as well as on a laptop. `aventure auth login --key` creates
and stores a personal API key through the same browser approval instead. In a
non-interactive environment, supply an existing key through `AUTH_TOKEN`. The
[CLI quickstart](/cli) walks through both, and the [MCP quickstart](/mcp)
covers OAuth and personal-key clients.

## Connect an MCP client with OAuth

The [MCP quickstart](/mcp#connect-to-the-hosted-server) owns the hosted URL,
public client ID, callback configuration, and first connection check. MCP
requires authentication even for tools that call anonymous API operations.

## Verify personal API access

Send your personal key or OAuth access token as a bearer token:

```bash
curl -H "Authorization: Bearer $AUTH_TOKEN" \
  "https://api.aventure.vc/v1/auth/me/permissions"
```

This checks which permissions the API grants your identity. A successful
sign-in does not enable every operation: plain-English search also requires a
current Pro subscription or trial. Use [Settings → Subscription](https://aventure.vc/settings/subscription)
to inspect your plan, or [contact support](/support) about service access.
Filtered public lists remain available without a subscription.

## Service integrations

An integration issued a client secret sends it as `X-Client-Secret`. Public
users use their own bearer credential instead. Administrative keys mentioned
in an endpoint's security declaration are managed by aVenture and are not a
prerequisite for public developer access.

## Which endpoints accept what

Read the `security` block on each endpoint in the reference rather than assuming
from the HTTP method. Two rules explain most of the surface:

- **A `POST` is not always a write.** Search, batch, and filter
  endpoints take a JSON body because their query is too large for a query string
  — `POST /v1/entities/search`, `POST /v1/search/all`, and `POST /v1/people/detail/batch`
  are all reads, and all accept a client secret. `POST /v1/search/all` also
  accepts a public user's bearer token and requires a current Pro subscription
  or trial for that user.
- **Authentication flows have their own requirements.** Follow the declared
  security and request parameters for each operation.

## Keeping credentials safe

Credentials are bearer-equivalent: anyone holding the string has the
access it grants. Keep them server-side, load them from your secret manager at
runtime, and never ship one in browser code or commit one to a repository.

## When authentication fails

A missing, malformed, or unrecognized credential returns `401`. A credential
that is valid but not permitted on that endpoint returns `403`. Both arrive in
the standard [problem detail](/errors) body, whose `detail` field names the
specific reason.
