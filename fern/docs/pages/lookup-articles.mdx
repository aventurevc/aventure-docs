An article lookup reads one article, extracts every company and person it
names, and identifies each name as [`POST /v1/lookup`](/lookup) would, with the article
as the source. It shares the lookup's [plan requirement](/lookup#access-and-limits).
To identify more names than an article job's limit, or a list of names you
already hold, start a [bulk lookup job](/lookup-jobs) instead.

## Choose an Article Path

| Need | CLI | Result |
|---|---|---|
| One synchronous JSON response from an article, screenshot, or supplied mention names | `aventure lookup-mentions --source-url "<article-url>"` (or `--file "<image>"`, `--mention-name ...`) | Identifications only; it creates no records or research runs |
| Asynchronous article processing | `aventure lookup-jobs create --source-url "<article-url>"` | Identifications, plus a record for each confirmed new name, usually with a research run |
| Bounded identification-only work | `aventure lookup-jobs create --max-names 8 --source-url "<article-url>"` or repeated `--mention-name` | Identifications only; it creates no records or research runs |

Use the synchronous path when you need the answer in one response. Use the
asynchronous job when the article may name companies or people aVenture does
not have yet. Use `--max-names` when you want a bounded batch of
identifications and will continue the article yourself.

1. Start the job with `POST /v1/lookup-jobs` and a body holding `sourceUrl`,
   `sourceNewsId`, or both. The call returns `202` with a `jobId`. Sending the
   same article again soon returns the earlier job.
2. Read the job with `GET /v1/lookup-jobs/{jobId}` until `state` is
   `COMPLETED` or `FAILED`. Only the caller that started the job can read it.
3. Act on each entry in `mention`. Every entry has the `name` as the article
   writes it and a `mentionType` of `COMPANY`, `PRODUCT_SERVICE`, or `PERSON`:
   - `identification` is the lookup answer, read exactly as in
     [Act on the answer](/lookup#act-on-the-answer).
   - `shell` is set when the answer is `NO_MATCH` and the job filed a new
     record for the name, or found a record aVenture already holds for the
     subject's website. The job files one only when the article and the
     subject's own live website both name it. `shell` holds the record's
     `entityId` or `personId`; when `enrichmentRunId` is present, it names the
     research run that fills in the profile. Filing it costs nothing.
   - `shellDetail` says, in one sentence, why no new record was filed for a
     `NO_MATCH` name.
   - `failureReason` replaces `identification` when a name could not be
     identified. Send that name alone to `POST /v1/lookup`.

When the job is accepted it spends one natural-search call to read the article
and one name-identification call for each name it may identify, up to its
per-article limit. A repeat of the same article that
returns the earlier job spends nothing. The job answers `402` and `429` under
the same rules as a single lookup.

## Example

Set `ARTICLE_URL` to the article's address and start a job:

<CodeBlocks>
```bash title="curl"
curl -X POST "https://api.aventure.vc/v1/lookup-jobs" \
  -H "Authorization: Bearer $AUTH_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"sourceUrl":"'"$ARTICLE_URL"'"}'
```

```bash title="CLI"
aventure lookup-jobs create --source-url "$ARTICLE_URL"
```
</CodeBlocks>

Read the job with the returned `jobId` until `state` is `COMPLETED`:

<CodeBlocks>
```bash title="curl"
curl "https://api.aventure.vc/v1/lookup-jobs/$JOB_ID" \
  -H "Authorization: Bearer $AUTH_TOKEN"
```

```bash title="CLI"
aventure lookup-jobs get --job-id "$JOB_ID"
```
</CodeBlocks>

Collect the ids from each matched mention's `match.owner` and from each `shell`
without an `enrichmentRunId`, then [queue research](/research-updates) on the
ones worth updating.
